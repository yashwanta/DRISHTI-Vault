**TECHNICAL INCIDENT REPORT**

**RBK HTTP/WebSocket and 192.168.1.1 Findings**

Springfield RoboShop FleetManager | Incident of August 11, 2026

| **Field** | **Value** |
| --- | --- |
| System | USSPRAMRFLMGR260003 / Springfield RDS |
| Incident time | August 11, 2026, 21:50:20 CDT |
| Report date | August 13, 2026 |
| Scope | rbk crash, VPN listener traffic, dispatch recovery, retry storm, and memory |

| **Executive conclusion**<br>The incident contains three separate defects. Traffic from VPN address 10.2.222.5 likely triggered an exception-safety defect in rbk's HTTP/WebSocket listener. After robod restarted rbk, AMR-01 and AMR-11 were reconstructed in a resource-occupying state and alarm 52113 halted dispatch. Separately, rbk continuously retries 192.168.1.1:20204, apparently from stale or default charger-related configuration. The current evidence does not show that the retry storm or memory pressure caused the crash. |
| --- |

# Confidence and attribution

High confidence: the retained core identifies an unhandled Boost.Beast exception as the direct cause of rbk termination, and the logs place connections from 10.2.222.5 immediately before the abort.

Moderate confidence: 10.2.222.5 was the network trigger source. The available evidence does not establish intent or identify the exact program or authenticated VPN user.

Not established: that 192.168.1.1:20204, AMR-01/AMR-11, or memory exhaustion caused the original rbk crash.

## Observed operational impact

- rbk service interruption followed by automatic robod restart.

- Five submitted orders remained at vendor_state=CREATED with no robot assigned.

- Eight connected robots were idle at status 5 and were not blocked.

- No 52200 'robot is blocked' alarms occurred in the affected window.

- Dispatch recovered only after AMR-01 and AMR-11 were physically powered on.

# 2. RBK crash: direct technical cause

The retained core dump shows an exception escaping from the RDSOrderAdapter network handler:

boost::beast::http::read()  
  -> rds::ws::Session::run()  
  -> exception escapes Asio completion handler  
  -> std::terminate()  
  -> abort()  
  -> SIGABRT (signal 6)

The relevant source location is /app/plugins/RDSOrderAdapter/src/ws_server2.cpp:46. Session::run() uses a throwing form of boost::beast::http::read() on a network-facing socket without an effective exception boundary.

| **Meaning of SIGABRT**<br>SIGABRT is Linux signal 6. In this incident it indicates that the C++ runtime called abort() after std::terminate(). It was not an out-of-memory kill and does not show that an operator manually stopped rbk. |
| --- |

## Protocol clarification

The failing class belongs to an HTTP/WebSocket listener, but the exception occurred while Beast was parsing the initial HTTP request. The evidence does not prove that the client completed a WebSocket Upgrade handshake.

| **Preferred incident wording**<br>An invalid HTTP request to rbk's RDSOrderAdapter HTTP/WebSocket listener caused an unhandled Boost.Beast exception and terminated rbk. |
| --- |

## Required software correction

Use the error-code overload and close only the failed client session:

boost::beast::http::read(stream, buffer, message, ec);  
if (ec) {  
    // Log a bounded, sanitized error; close this session; return.  
}

The vendor should also audit every Beast/Asio callback in RDSOrderAdapter for throwing I/O calls and place a final exception boundary around each completion handler.

## Identity limitation

Neither the packet capture nor rbk logs contain a VPN username, email address, authenticated identity, or identifying cookie. The VPN administrator must correlate 10.2.222.5 with VPN authentication/address-assignment logs for 2026-08-11 21:50:19-21:50:20 CDT.

# 4. Listener configuration and exposure

rbk actively listens on TCP port 8088 on all interfaces. RoboShop model parameters reference RDSOrderAdapter with port value 8088, while local RDS application files use http://127.0.0.1:8088/.

| **Evidence** | **Interpretation** |
| --- | --- |
| rbk listener *:8088 | The interface is network reachable, subject to routing and firewall policy. |
| RDSOrderAdapter parameter value 8088 | The adapter supplies the HTTP/WebSocket listener implicated by the core. |
| Local Java connection to 127.0.0.1:8088 | Port 8088 has an internal application consumer. |
| Remote clients on 8088 | Multiple operational/dashboard clients also use the interface. |

## Observed current clients

The runtime snapshot showed connections from 10.222.10.153, 10.222.10.19, 10.222.10.151, 10.2.222.5, 10.2.1.52, and localhost Java. Some clients maintained more than one connection.

| **Operational caution**<br>Do not simply disable or firewall port 8088. It has valid internal and remote consumers. First identify required clients, apply source restrictions where supported, and deploy the exception-handling fix. |
| --- |

## Likely traffic contribution

At approximately 69.6 KB per request and one request per second, a single polling client receives roughly 245 MB per hour or about 5.7-6.0 GB per day. This is network traffic, not automatically retained memory, but multiple duplicate clients can increase rbk CPU and serialization load.

# 5. AMR-01/AMR-11 restart-recovery defect

Before the incident, AMR-01 and AMR-11 were powered off and intended to be out of service. After rbk restarted, they appeared to have changed from a non-resource-occupying state to a resource-occupying state while remaining physically disconnected.

| **State** | **Dispatch meaning** |
| --- | --- |
| Undispatchable & Offline | Does not accept orders and does not occupy dispatch resources. |
| Undispatchable & Online | Does not accept orders but continues to occupy dispatch resources. |

In this user interface, Online describes dispatch/resource policy; it does not prove physical connectivity.

## Failure chain after restart

rbk restart  
  -> scene/state reconstruction  
  -> AMR-01 and AMR-11 remain physically disconnected  
  -> robots remain unignored and undispatchable-online  
  -> alarm 52113  
  -> global dispatch gate  
  -> healthy robots receive no orders

## Alarm 52113

The product documentation identifies 52113 as ERR_reboot_robots_disconnect: 'Unignore robot is disconnect.' During the incident it did not time out, quarantine the two disconnected robots, or permit unrelated healthy robots to continue dispatching.

Manual recovery consisted only of powering on AMR-11 and AMR-01. Alarm 52113 then stopped and dispatch resumed immediately, which strongly ties the dispatch halt to their recovered state.

## Required recovery behavior

- Persist and atomically restore ignored/unignored status.

- Persist dispatchable/undispatchable and online/offline resource occupancy separately.

- Reconcile persisted policy against current physical connectivity at startup.

- Do not silently promote a disconnected out-of-service robot into a resource-occupying state.

- Prevent one disconnected robot from globally blocking healthy robots unless an explicit safety dependency requires it.

# 6. 192.168.1.1:20204 retry storm

The restarted rbk process owns an outbound TCP connection loop from FleetManager 10.222.10.76 to 192.168.1.1:20204. The destination never responds.

| **Metric** | **Finding** |
| --- | --- |
| New attempts | One every approximately 4 seconds |
| TCP behavior | Three SYN transmissions for each source port/attempt |
| Responses | None observed |
| Estimated rate | Approximately 900 attempts/hour |
| Daily estimate | Approximately 21,600 attempts and 64,800 SYN packets/day |
| Process owner | rbk PID 3999961 in the captured runtime |

The reported count of 310,552 is unlikely to represent distinct TCP connections at the measured rate. It more likely represents application operations, retry log lines, or duplicate ingestion.

## Configuration findings

The address 192.168.1.1 appears in charger and charger-spot files under multiple robot model folders. For AMR-01, the normal charger selection is None and the charger-spot selection reports SEER. However, at least eight model folders contain the same SEER branch and 192.168.1.1 values.

AMR-01's charger-related files were last modified in March 2026, months before the incident. The address was therefore not introduced during the August restart. rbk.cfg was the only file proven rewritten by robod at restart, and the supplied rbk.cfg reference search did not locate the address.

| **Configuration conclusion**<br>192.168.1.1 resembles a shared vendor default or stale endpoint. The available evidence does not yet prove which active runtime configuration object generates the connection to port 20204. |
| --- |

| **Change-control caution**<br>Do not globally replace 192.168.1.1, substitute an arbitrary address, or remove charger objects directly in production. Compare the selected charging method with a working robot using the same physical charger, back up the model, and make the supported change through RoboShop. |
| --- |

## Verification criteria

- Malformed HTTP requests return an error or close only the client session; rbk remains running.

- Restart testing preserves AMR-01/AMR-11 as Undispatchable & Offline when they were previously out of service.

- Alarm 52113 does not prevent healthy robots from receiving unrelated orders indefinitely.

- No SYN_SENT traffic remains to 192.168.1.1:20204 after the approved configuration correction.

- rbk and Java memory trends are bounded or have documented operational limits.

# 9. Vendor defect statements

## Defect 1 - Unhandled listener exception terminates rbk

An invalid HTTP request to the RDSOrderAdapter HTTP/WebSocket listener causes boost::beast::http::read() to throw. The exception escapes through the Asio completion handler and invokes std::terminate(), aborting rbk. Network input errors must be handled per session and must not terminate the fleet engine.

## Defect 2 - Restart recovery changes offline resource state

After an rbk crash and robod restart, disconnected robots previously intended as Undispatchable & Offline were reconstructed as Undispatchable & Online while remaining unignored. Alarm 52113 then globally blocked dispatch until both robots were powered on. Startup recovery must preserve the complete state or safely reconcile it against live connectivity.

## Defect 3 - Persistent stale endpoint retry

rbk repeatedly opens outbound TCP connections to 192.168.1.1:20204 every four seconds with no response. The product must expose which runtime configuration object owns the endpoint, apply bounded backoff, and avoid unbounded retry/log noise for unreachable devices.

## Evidence limitations

- No packet capture from the exact August 11 crash window was retained.

- The later PCAP contains valid HTTP traffic and cannot reconstruct the malformed incident request.

- VPN username/email cannot be derived from the server PCAP; VPN gateway logs are required.

- The exact active runtime object generating 192.168.1.1:20204 remains unidentified.

- The two approximately 700 MB recursive search outputs include minified JavaScript, maps, libraries, historical logs, and documentation; raw match counts are not reliable incident counts.

- The short memory sample establishes retained memory but is insufficient to prove or exclude a slow leak.
